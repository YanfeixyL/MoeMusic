# 每日推荐刷新逻辑审查

## 现有问题

首页原本只在 `Home.vue` 首次挂载时请求 `/everyday/recommend`。首页属于 `KeepAlive` 页面，切回首页不会重新挂载；即使手动刷新页面，API 服务也会对相同 URL 的成功响应缓存 2 分钟。因此“刷新后歌曲几乎不变”同时可能来自页面缓存和 API 缓存。

原实现还会对返回的 `song_list` 做随机排序。随机排序只改变顺序，不会生成新的歌曲。

## 本次实现

点击“刷新推荐”按钮后，`Home.vue` 会并行请求：

1. `/everyday/recommend?platform=ios&timestamp=...`：主每日推荐入口。
2. `/recommend/songs?platform=android&timestamp=...`：同一 API 服务提供的备用每日推荐入口，使用不同的平台参数和请求体结构。
3. `/everyday/history?mode=list&platform=ios&timestamp=...`：读取近期历史推荐列表，补充每日入口没有返回的新 hash。
4. `/home/discover`：调用上游新增的首页刷歌推荐接口；该接口在 API 子模块中使用签名请求体和数值默认参数，避免向上游传递字符串数字。
5. `/top/card?card_id=...&timestamp=...`：从 1、2、3、4、6 五个精选卡片类型中轮换一个，补充可能不同的推荐候选。

`timestamp` 只用于改变本地 API 的缓存键，不会被当成酷狗“换一批”参数。API 服务根据请求头中的 `Authorization` 继续传递账号和设备信息。

`src/utils/recommendations.js` 对多个响应做以下处理：

- 兼容 `song_list`、`songs`、首页刷歌 `items[].song_info`、历史推荐 `lists[].song_list` 和数组形式的候选列表；
- 以大写 hash 去重；
- 统一歌曲名、封面、作者和时长字段，避免不同推荐接口的字段差异影响播放；
- 优先选择本次会话尚未展示的歌曲；
- 上游没有返回足够新歌曲时，使用候选集合并旋转顺序，避免把“顺序变化”误认为“新数据”；
- 仅在内存中记忆最多 200 个 hash，不写入账号数据或永久存储。

首次进入首页仍只请求每日推荐，避免改变原有启动流量。刷新按钮才启用备用来源和去重策略。

API 子模块已从固定提交 `a5a98013cce79fe0ae2ad65fc84b68176ebcfc1e` 更新到上游 `ba3645f2c89e6b9d4fec82ff783c15287e4c5f43`。上游文档明确说明 `/home/discover` 的 `today_play_num` 会影响去重与排序，但该项目的 HTTP 查询参数到达模块时均为字符串；因此本次使用上游模块的数值默认请求，避免触发酷狗服务的类型错误，并通过客户端 hash 记忆承担最终去重。

## 不能保证的部分

酷狗 API 文档没有公开“强制生成新一批每日推荐”的参数。以上逻辑只能增加候选来源、绕过本地两分钟缓存并减少重复展示，不能保证酷狗服务端一定返回新歌曲。如果三个入口返回相同候选，界面只能轮换顺序。

`/top/card` 和 `/recommend/songs` 的推荐语义不同，混合后可能包含精选卡片或平台推荐歌曲；如果产品必须严格保持“每日推荐”含义，应去掉这两个补充来源，只保留每日推荐入口并接受上游重复结果。

推荐缓存目前仍由 API 服务按完整 URL 建键，没有按用户 ID 单独分区。共享一个 API 服务给多个账号时，后续应在 API 缓存键中加入账号/设备维度，避免缓存串号。

## 验证

`tests/recommendations.test.js` 覆盖了 hash 去重、优先未展示歌曲、无新候选时的顺序轮换和会话记忆上限。当前工作树缺少完整 `node_modules`，所以全量 `npm test` 和生产构建还需要在安装依赖后运行；推荐工具的四项单元测试已单独通过。
