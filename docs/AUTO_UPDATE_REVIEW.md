# 自动更新改动说明与审查指南

本次修改针对桌面版的更新检查、下载、安装和发布流程。所有改动保留在本地工作区，尚未提交、推送或发布安装包。

## 1. 原有逻辑与发现的问题

本次检出的主项目版本为 `1.7.0`。项目采用 Vue/Vite 渲染界面、Electron 主进程管理桌面功能，音乐 API 是固定提交的 Git 子模块，并被打包为独立可执行文件。

项目已经依赖 `electron-updater`，也有在线更新按钮，并非完全没有更新实现。原来的链路存在以下问题：

| 位置 | 原有行为 | 影响 |
| --- | --- | --- |
| `electron/services/updater.js` | 关闭自动下载和退出安装 | 依赖用户主动检查并选择下载 |
| `electron/main.js` | 初始化更新器，但启动后不调用检查 | 启动时不会自动获取新版本 |
| `electron/services/updater.js` | 重写 `app.isPackaged`，始终返回 `true` | 开发环境也可能触发真实更新；破坏 Electron 的环境判断 |
| 更新检查/下载入口 | 依赖全局 `silentCheck` 和更新器内部的 `updateInfoAndProvider` | 并发入口互相影响；依赖内部实现细节 |
| `AppUpdateDialog.vue` | IPC 下载调用完成后再次把界面设置为“下载中” | 下载完成事件先到时，界面可能退回下载状态 |
| `AppUpdateDialog.vue` | 自行请求 GitHub API，与主进程各自维护状态 | 重复网络请求，页面重建后可能丢失更新进度 |
| `electron/main.js` | `before-quit` 中异步调用 `app.exit(0)` | 退出生命周期可能被截断，影响更新器的退出安装回调 |
| `.github/workflows/release.yml` | 生成新标签，但打包前没有同步 `package.json` 版本 | 标签、安装包内部版本和更新元数据可能不一致 |
| `.github/workflows/release.yml` | 任意平台上传时就公开 Release | 用户可能先看到不完整的跨平台发布 |

**关于“不更新就不能使用”：没有在已检查的主项目启动、请求、更新代码及固定 API 子模块中发现按 MoeKoe 应用版本强制禁用整个播放器的逻辑。** 插件管理里有插件最低版本限制，但它不是音乐播放的全局开关。API 请求使用自己配置的酷狗 `clientver` 等参数，与 MoeKoe 的应用版本不同。

接口变化、鉴权/风控、API 子模块兼容性或网络问题都可能造成旧版不能播放。本次没有旧版本运行日志和故障复现，不能确认用户遇到的具体原因；自动更新有助于交付修复，但不能保证所有播放故障都会因此消失。API 子模块只初始化到仓库原有的固定提交，没有修改或升级它。

## 2. 更新后的执行流程

```text
Electron ready
  ├─ 初始化更新器（独立于音乐 API）
  │    ├─ 不支持的安装形式 → 保留手动更新
  │    └─ 支持的安装形式 → 10 秒后检查，此后每 4 小时检查
  └─ 启动 API 和窗口
       └─ 初始化失败 → 原生错误对话框提供“检查更新 / 退出”

检查稳定版 Release
  ├─ 无新版本 → 不下载；后台检查不弹窗
  ├─ 网络或元数据错误 → 清理进度、记录错误；允许手动重试
  └─ 有新版本 → 后台下载并由 electron-updater 校验
       ├─ 下载失败 → 保留重试与手动下载入口
       └─ 下载完成 → 提示安装
            ├─ 现在安装 → 调用 quitAndInstall(false, true)
            └─ 退出时安装 → 正常退出应用时由更新器安装
```

后台检查失败不会弹出错误框打断播放；托盘主动检查失败会显示说明。下载完成会弹出一次原生安装提示。关闭更新页面只关闭界面，不取消后台下载。

“退出时安装”指托盘退出、退出快捷键或设置为退出的关闭操作。关闭到托盘仍然保持运行，因此不会安装。强制结束进程、系统掉电等情况不属于正常退出。Windows 全机安装可能出现系统权限提示。

## 3. 修改部分的代码逻辑

### `electron/services/updateController.js`：可测试的更新状态与任务合并

新增一个不依赖 Electron UI 的控制器，通过参数接收真实更新器和状态回调。

- `supportsAutoUpdate()` 使用真实 `app.isPackaged` 和安装形式判断是否支持更新。
- 状态包括 `idle`、`checking`、`available`、`downloading`、`downloaded`、`not-available`、`unsupported`、`error`。
- `checkPromise`、`downloadPromise` 合并启动、托盘和页面的并发请求，避免重复检查与下载。
- `check()` 通过公开事件判断是否有新版本，随后显式调用 `downloadUpdate()`。不再访问 `updateInfoAndProvider`。
- 底层 `autoDownload = false` 是为了由控制器统一调度下载；检查到新版本后仍会自动下载，无须再次点击按钮。
- `autoInstallOnAppQuit = true`；下载完成前 `install()` 返回 `not-downloaded`。
- 明确关闭预发布更新和降级，具体版本选择、缓存、校验与安装交给 `electron-updater`。
- 捕获检查、下载和同步安装错误，重置任务锁，允许重试。
- `getState()` 返回独立快照，界面无法修改主进程内部状态。

### `electron/services/updater.js`：Electron 适配、定时检查与安装提示

- `setupAutoUpdater(() => mainWindow)` 只初始化一次，通过窗口获取函数处理窗口尚未创建或重新创建的情况。
- 使用 electron-builder 根据 `package.json` 的 `build.publish` 生成的 `app-update.yml`；不再硬编码覆盖下载源。
- 启动延迟 10 秒检查，此后每 4 小时检查；退出时清理定时器。
- 把状态发送到主窗口的 `update-state` 事件，并同步任务栏进度。
- 下载完成显示安装提示，用一个共享 Promise 避免叠加提示。
- 后台错误通过更新器日志和状态反馈；手动检查会显示检查结果。

### `electron/main.js`、`electron/appServices.js`：启动和退出生命周期

- 更新器初始化移到 API 启动之前；API 失败时仍然可以通过原生对话框检查和下载修复版本。
- `before-quit` 设置 `app.isQuitting = true`，防止“关闭到托盘”拦截更新退出。
- 移除退出清理里的 `app.exit()`；同步启动清理操作，让 Electron 正常发出 `quit`，由更新器处理退出安装。
- 清理步骤分别捕获异常，避免一个服务清理失败阻止后续清理。
- 关闭窗口时避免在已经退出的情况下再次调用 `app.quit()`。
- 停止 API 子进程前检查 PID、退出状态和 killed 标志，避免对已结束进程再次发信号。
- 更新相关 IPC 只接受主窗口的主框架请求；渲染进程不能传入下载 URL、文件路径或自定义安装命令。

### `electron/preload.cjs`、`src/components/AppUpdateDialog.vue`：状态同步与安装入口

新增 `getUpdateState()`、`installUpdate()` 和 `onUpdateState()`，保留原下载入口。

- 订阅事件后读取快照；如果期间已经收到较新的状态事件，则忽略旧快照。
- 页面进度、按钮和状态文字都来自主进程状态；下载 IPC 完成后不会再覆盖下载完成状态。
- 下载完成的按钮可再次执行“立即重启安装”，无需依赖第一次原生提示。
- 更新页面重新挂载时恢复主进程状态；卸载时使用 preload 返回的解绑函数清理监听。
- 网页版和不支持自动更新的安装形式才通过 GitHub Releases API显示新版提示。
- 网页请求增加超时、HTTP 状态检查和请求取消；手动入口打开 Release 页面，由用户选择正确 CPU 架构的安装包。
- 原更新组件已采用中文界面，本次沿用；主进程安装提示同步修改了现有六种语言文案。

### `src/utils/appUpdate.js`、`package.json`、`package-lock.json`

- 增加 `semver` 为直接生产依赖，替换不支持预发布版本的点分数字比较。
- 发布说明兼容字符串和更新器的完整 changelog 数组。
- 新增 `npm test`，使用 Node 内置测试运行器；没有引入额外测试框架。
- 锁文件中的 semver 依赖布局随直接依赖调整；保留原有平台包的 libc 限制。

### `.github/workflows/release.yml`：完整发布后才对客户端可见

1. 创建绑定本次提交的草稿 Release。
2. 每个平台在构建前执行 `npm version <新标签> --no-git-tag-version --allow-same-version`，使前端版本、安装包版本、更新元数据版本与 Release 一致。
3. 运行测试和构建，上传安装包、`.blockmap` 和 `latest*.yml`，保持草稿状态。
4. 独立的 `publish-release` 任务依赖全部平台成功，最后才公开 Release。任意平台失败时草稿不会公开。

构建时的版本注入不会向 Git 自动提交或推送版本修改。

## 4. 平台支持与更新源

| 环境 | 本次行为 | 原因/前提 |
| --- | --- | --- |
| Windows NSIS 安装版 | 自动检查、后台下载、重启或退出安装 | 仓库当前的 Windows 打包目标；需发布正确的 `latest.yml` 和对应安装包 |
| Linux AppImage | 自动检查、后台下载、重启或退出安装 | 运行环境有 `APPIMAGE`；更新文件所在目录需允许写入 |
| Linux deb | 手动更新 | 本次不增加包管理器提权安装逻辑 |
| macOS | 手动更新 | 当前 `build.mac.identity = null`，没有签名，无法直接使用要求签名的 Squirrel.Mac 更新机制 |
| 开发环境、网页版、其他形式 | 手动入口/发布提示 | 不伪造打包状态，不在源码运行时安装桌面更新 |

**首次启用仍需安装包含本改动的构建。** 修改本地源码不会给已经安装的旧客户端远程注入更新能力。

当前仓库的 `build.publish` 仍指向官方 `MoeKoeMusic/MoeKoeMusic`。如果这份改动提交并合并到官方，后续官方安装包可以继续保留该功能。如果你独立维护 fork，应在正式分发前把 `build.publish` 改为自己控制的发布仓库，同时调整更新页面中的手动 Release/API 地址。否则自定义构建后续可能安装上游官方包，从而覆盖本地定制功能。

没有新增代理或第三方下载源，也没有跳过更新器的校验。SHA-512 用于检查下载内容与发布元数据一致，不等同于发布者身份签名；若配置签名，应沿用相同的发布者身份。macOS 完整自动更新需要后续独立配置签名、公证及真实安装测试。

## 6. 发布前仍需进行的安装验收

建议维护者在隔离测试仓库和测试账号/系统中准备版本 A、B；让 A 包含本次改动并指向测试发布仓库，让 B 的版本高于 A。不要用真实官方源做会覆盖个人定制的实验。

1. 安装 A、启动并等待，确认自动找到 B、只下载一次、播放不中断、任务栏和页面进度同步。
2. 下载过程中切换顶栏/侧栏或重新打开页面，确认状态仍正确。
3. 下载完成后选择立即安装，确认 A、歌词窗口及 API 子进程退出，B 启动且用户配置保留。
4. 重新测试选择退出安装，确认正常退出后安装；关闭到托盘时不安装。
5. 模拟网络失败后恢复，确认后台不频繁弹错，手动重试能继续完成。
6. 用错误 SHA-512/缺失安装包的测试发布验证真实更新器拒绝安装。
7. Windows 覆盖普通权限和全机安装的提权场景，并验证当前构建产生的通用/架构安装包与 `latest.yml` 匹配；Linux 验证 AppImage 可写/只读目录。
8. 验证 API 二进制缺失或启动失败时，原生错误对话框中的更新入口仍能下载并安装。
9. 检查 GitHub Actions：任意平台失败时 Release 保持草稿；全部成功后才公开；标签、包版本、更新元数据和上传文件一致。

以上真实安装验收通过后，才能确认自动更新在目标操作系统上端到端可用。
